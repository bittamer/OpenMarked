# OpenMarked 0.3.0 Implementation Plan

## Milestone Summary

OpenMarked `0.3.0` is the Markdown Power Pack release.

The goal is to make OpenMarked noticeably better for developers, documentation authors, academics, and technical writers while keeping the app local-first, native, beautiful, and easy to understand.

Headline features:

- Mermaid diagram rendering.
- KaTeX math rendering.
- GitHub-style alerts and callouts.
- Link validation for local files, headings, and document-relative references.

Supporting work:

- Rich Markdown settings.
- Rich-content diagnostics.
- Export and print readiness for rendered diagrams and math.
- Visual QA fixtures and screenshots.
- Documentation for privacy, limitations, and supported syntax.

## Product Goals

1. Render common technical Markdown documents without requiring a remote service.
2. Preserve OpenMarked's current security posture: user-authored scripts stay blocked, and only trusted app-owned JavaScript is injected.
3. Make rich Markdown feel native and polished in preview, export, print, screenshots, and diagnostics.
4. Keep defaults easy: a new user should open a README and see diagrams, math, callouts, and link warnings without configuring a pipeline.
5. Make behavior predictable for GitHub-authored README files, especially callouts, heading fragments, task lists, and relative links.

## Non-Goals

These are intentionally deferred unless they become required to finish the 0.3.0 features safely.

- Arbitrary user JavaScript execution.
- CDN-hosted Mermaid, KaTeX, CSS, fonts, or runtime assets.
- A general plugin API.
- A full custom Markdown parser.
- Perfect GitHub rendering parity for every edge case.
- Continuous background crawling of remote links.
- DOCX, EPUB, or publishing-workflow exports.
- Folder-wide wiki navigation, backlinks, or project graphs.
- Interactive Mermaid editor tooling.
- Equation numbering and cross-reference management.

## MVP Scope For 0.3.0

### In Scope

- Fenced Mermaid blocks using code fence info strings such as `mermaid`.
- Display and inline KaTeX math using common delimiters.
- GitHub alert blockquotes:
  - `[!NOTE]`
  - `[!TIP]`
  - `[!IMPORTANT]`
  - `[!WARNING]`
  - `[!CAUTION]`
- Local link diagnostics for:
  - missing document-relative files
  - missing document-relative images
  - missing same-document heading fragments
  - malformed URLs
  - unsupported link schemes
- Optional cross-document heading checks for linked Markdown files when the target file is small and readable.
- Manual or opt-in remote link checking design, with implementation deferred unless the local validator lands early.
- Standalone HTML, PDF export, print, and snapshot readiness for Mermaid and KaTeX.
- Settings for enabling rich features and controlling network behavior.

### Stretch Scope

- Full GitHub README compatibility mode as a visible render profile.
- Remote HTTP(S) link validation through a manual "Check Remote Links" action.
- Per-feature toolbar indicators.
- Copy rendered Mermaid SVG.
- Copy rendered equation source or MathML.

## Architecture Principles

- Keep renderer behavior in `OpenMarkedCore`.
- Keep WKWebView orchestration in `OpenMarkedApp`.
- Keep theme styling in theme resources and shared CSS assembly.
- Keep document content local by default.
- Load rich-content JavaScript and CSS only when a document uses the relevant feature.
- Treat Mermaid and KaTeX runtimes as trusted app assets, never as document assets.
- Surface every rich-content failure as a `RenderDiagnostic` where practical.
- Do not make export or print depend on a live network connection.

## Current Architecture Fit

The existing pipeline is a good foundation:

1. `CMarkGFMRenderer` renders Markdown through `cmark-gfm`.
2. `HeadingPostProcessor` adds stable heading IDs and builds the native outline.
3. `CodeHighlighter` highlights supported code fences offline.
4. `RenderDiagnosticsCollector` reports missing local images.
5. `HTMLDocumentAssembler` creates the full preview document with theme CSS.
6. `PreviewWebView` sanitizes preview HTML before loading it into `WKWebView`.
7. `PreviewWebView` injects app-owned JavaScript helpers through `evaluateJavaScript`.
8. Export and print reuse the rendered document and WebKit.

0.3.0 should extend this pipeline instead of replacing it.

Proposed render pipeline:

1. Load Markdown document.
2. Render CommonMark/GFM through `cmark-gfm`.
3. Add heading IDs and outline.
4. Transform GitHub callout blockquotes.
5. Transform Mermaid code fences into rich diagram placeholders.
6. Transform math delimiters into KaTeX placeholders.
7. Highlight ordinary code blocks while skipping rich placeholders.
8. Apply content policy for remote images and unsafe links.
9. Collect diagnostics for images, links, headings, Mermaid placeholders, and math placeholders.
10. Assemble the full HTML document with theme CSS and rich-content asset hooks.
11. Load sanitized HTML into `WKWebView`.
12. Inject only the trusted app-owned runtime helpers required by this document.
13. Notify export, print, and snapshot code when async rich rendering is complete.

## Dependency Policy

Mermaid and KaTeX should be bundled locally and pinned.

Requirements:

- Record exact versions.
- Record license text and attribution.
- Keep assets in SwiftPM resources or generated resource bundles that `Scripts/package_release.sh` already copies.
- Do not load assets from CDN by default.
- Prefer minified release files for runtime, plus readable source/version metadata in documentation.
- Add an update note explaining how to refresh bundled assets.

Candidate asset layout:

```text
Sources/OpenMarkedCore/Resources/RichContent/
  Mermaid/
    mermaid.min.js
    LICENSE
    VERSION
  KaTeX/
    katex.min.js
    katex.min.css
    fonts/
    LICENSE
    VERSION
  OpenMarked/
    rich-content.css
    rich-content-runtime.js
```

## Phase Order

Recommended implementation order:

1. Foundation, fixtures, dependency decisions, and settings model.
2. Callouts, because they are pure HTML/CSS and immediately improve README rendering.
3. Link validation, because it builds on existing diagnostics and adds high user value without JavaScript.
4. Rich-content asset pipeline.
5. Mermaid rendering.
6. KaTeX rendering.
7. Export, print, snapshot, and visual QA hardening.
8. Documentation, release notes, and tag prep.

This order keeps the first half of the milestone mostly Swift and CSS, then isolates the more delicate WKWebView runtime work.

## Phase 2: Link Validation

### 0.3-200: Build Link Reference Extractor

Description:

Extract links from rendered HTML and normalize them relative to the source document.

Implementation notes:

- Extend the existing local image extraction approach.
- Extract `<a href="...">` references.
- Decode entities and percent-encoded paths carefully.
- Ignore empty anchors intentionally used as placeholders.
- Preserve original source strings for diagnostics.

Acceptance criteria:

- Extracts relative files, absolute file URLs, same-document fragments, mailto URLs, and HTTP(S) URLs.
- Does not treat code examples as real links.
- Deduplicates repeated links for diagnostics while preserving counts for future inspectors.

### 0.3-201: Validate Local File Links

Description:

Report document-relative links whose target files do not exist.

Rules:

- `./guide.md` resolves against the source document directory.
- `../assets/logo.png` resolves against the source document directory.
- `file:///...` resolves as an absolute local file.
- `#section` is not a file link and is handled by heading validation.
- `https://`, `http://`, `mailto:`, and `tel:` are not local file links.

Acceptance criteria:

- Missing local file links produce warnings.
- Existing local file links produce no warnings.
- Directory links are treated as valid if the directory exists.
- Local image diagnostics continue to work.
- Tests cover spaces, percent escapes, query strings, and fragments.

### 0.3-202: Validate Same-Document Heading Fragments

Description:

Report links to heading IDs that do not exist in the current document.

Implementation notes:

- Use the final heading IDs from `HeadingPostProcessor`.
- Support percent-decoded fragments.
- Treat empty fragments as no-op links.
- Respect any future GitHub compatibility slug mode.

Acceptance criteria:

- `[Good](#existing-heading)` is valid.
- `[Bad](#missing-heading)` produces a warning.
- Duplicate headings and generated suffixes are handled.
- Existing custom heading IDs are respected.

### 0.3-203: Validate Cross-Document Markdown Heading Fragments

Description:

When a local link points to another Markdown file with a fragment, validate the target file and target heading if practical.

Implementation notes:

- Keep this local-only.
- Limit target file size to avoid surprising work.
- Use a lightweight heading scanner or the renderer without loading assets.
- Do not recursively validate links in the target document.

Acceptance criteria:

- `other.md#heading` is valid when the file exists and the heading exists.
- `other.md#missing` warns when the file exists but the heading is missing.
- Large or unreadable target files produce an informational diagnostic, not a crash.
- Security-scoped access behavior remains compatible with user-opened files.

### 0.3-204: Classify Remote Links Without Crawling

Description:

Parse remote URLs enough to report malformed URLs, unsupported schemes, and blocked network validation status without making network requests.

Acceptance criteria:

- Valid `http` and `https` URLs are classified.
- Malformed URL strings produce a warning only when clearly link-like.
- Unsupported schemes produce a warning or info diagnostic depending on risk.
- No network request is made during normal rendering.

- Link diagnostics popover with mixed warnings.

### Performance Checks

- Render a document with at least 20 diagrams.
- Render a document with at least 200 inline equations.
- Render a long README with many links.
- Confirm live preview debounce still prevents excessive reloads.
- Confirm snapshot and PDF timeouts are high enough for legitimate rich documents but low enough to fail predictably.

## Security And Privacy Checks

- No remote Mermaid or KaTeX assets are loaded by default.
- User-authored scripts are stripped before preview.
- User-authored inline event handlers are stripped before preview.
- Mermaid runs in the safest practical security configuration.
- KaTeX uses `trust: false`.
- Local link validation does not read unrelated files except the explicit linked paths being validated.
- Remote link validation is disabled by default.
- If remote link validation is implemented, it must be manual or opt-in and cancellable.
- Diagnostics do not upload or transmit document contents.

## Accessibility Checks

- Callout titles are text, not color-only signals.
- Mermaid figures have accessible labels.
- Math rendering keeps readable text alternatives where KaTeX supports them.
- Inline errors are reachable and readable.
- Diagnostics are keyboard reachable.
- Rich content does not break reduced-motion settings.
- Theme contrast remains acceptable in light and dark modes.

## Release Exit Criteria

0.3.0 is ready when:

- Mermaid, KaTeX, GitHub callouts, and local link validation are implemented.
- Rich Markdown fixtures render in preview.
- Rich Markdown fixtures export to standalone HTML.
- PDF export and Print include rendered diagrams and math.
- Diagnostics report broken local links and heading fragments.
- No runtime feature requires a network connection.
- Settings expose meaningful rich-content controls.
- README and docs explain supported syntax and limitations.
- Visual QA screenshots are refreshed.
- `swift build` passes.
- `swift run OpenMarkedVerifier` passes.
- `swift test` passes where XCTest is available.
- `Scripts/verify_release.sh` passes before publishing artifacts.

## Open Questions

1. Should inline `$...$` math be enabled by default, or should only `$$...$$` display math ship first to avoid currency false positives?
2. Should remote link checking be part of `0.3.0`, or should `0.3.0` ship local validation only and defer network checks to `0.3.1`?
3. Should Mermaid source remain visible behind a disclosure control, or should it be hidden after successful rendering?
4. Should GitHub README compatibility be a visible user setting in `0.3.0`, or an internal profile that becomes visible later?
5. Should exported standalone HTML embed Mermaid and KaTeX JavaScript by default, or reference adjacent asset files to keep the HTML smaller?

## Recommended Cut Line

If the milestone gets large, keep:

- GitHub callouts.
- Local file and same-document heading validation.
- Mermaid preview rendering.
- KaTeX preview rendering.
- PDF/export readiness for documents that use bundled assets.
- Documentation and visual QA.

Defer:

- Remote link crawling.
- Full visible GitHub README compatibility mode.
- Cross-document heading validation for large files.
- Mermaid source copy controls.
- Equation numbering.
- Custom per-document rich-content settings.
