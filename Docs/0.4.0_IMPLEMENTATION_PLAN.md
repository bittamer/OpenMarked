# OpenMarked 0.4.0 Implementation Plan

## Milestone Summary

OpenMarked `0.4.0` is the Document Workbench release.

`0.3.0` made OpenMarked render richer Markdown. `0.4.0` should make OpenMarked more useful after rendering: inspect the document, understand its metadata, review references and assets, polish themes, and prepare print/PDF output with confidence.

Headline features:

- Native document inspector sidebar.
- Front matter and metadata inspector.
- Links and images/assets inspector.
- Rich document statistics.
- Current section tracking and outline polish.
- Theme manager with custom CSS import.
- Print-specific controls and export readiness checks.

Supporting work:

- Expanded inspection model in `OpenMarkedCore`.
- Better diagnostics grouping and source navigation hooks.
- Settings and persistence for inspector, user themes, and print controls.
- Visual QA coverage for inspector states, custom themes, and print controls.
- Documentation for inspecting and theming documents.

## Product Goals

1. Keep OpenMarked a viewer and preview companion, not a Markdown editor.
2. Help users answer "is this document ready?" without leaving the preview.
3. Make document structure, metadata, references, diagnostics, and assets visible in one native workspace.
4. Make themes feel manageable now that OpenMarked has many built-in styles.
5. Preserve the local-first privacy posture: no background network crawling, no user-authored JavaScript execution, no remote theme dependencies.
6. Improve export and print confidence without pulling full publishing workflows into `0.4.0`.

## Product Inspiration

These references are inspiration, not feature parity requirements:

- Typora documents outline navigation, current-header highlighting, outline filtering, and outline export:
  `https://support.typora.io/Outline/`
- Typora exposes word count, character count, line count, and reading time:
  `https://support.typora.io/Word-Count/`
- Typora export behavior includes repeated export using previous settings:
  `https://support.typora.io/Export/`
- Obsidian properties show how front matter can become structured note metadata:
  `https://help.obsidian.md/properties`
- Obsidian backlinks and local graph show the value of local context around the active document:
  `https://help.obsidian.md/plugins/backlinks`
  `https://help.obsidian.md/plugins/graph`
- Zettlr positions writing statistics, project support, themes, and markdown linting as useful writing-workbench features:
  `https://www.zettlr.com/features`

OpenMarked should borrow the useful ideas while staying narrower: native preview, local document inspection, no editing surface, no full vault graph yet.

## Non-Goals

These are intentionally deferred unless they become required to finish `0.4.0` safely.

- A Markdown editor.
- Full folder workspace, global graph, or vault database.
- Full backlink graph visualization.
- DOCX, EPUB, RTF, or Pandoc export.
- Full export profiles and preset editor.
- Plugin API or marketplace.
- Remote link crawling by default.
- Remote theme downloads.
- JavaScript-based user themes.
- AI, grammar checking, or remote proofreading.
- Perfect source-position mapping for every rendered HTML node.

## MVP Scope For 0.4.0

### In Scope

- Right inspector sidebar with tabs or segmented views.
- Front matter inspector for YAML/TOML/JSON front matter already parsed by OpenMarked.
- Metadata rows for title, description, date, tags, author, custom fields, file path, modified time, file size, and document type.
- Links inspector for rendered anchors and link diagnostics.
- Assets inspector for local images and missing images.
- Diagnostics inspector with grouping, filtering, and actions.
- Statistics panel with richer document metrics.
- Current section highlight in the outline based on preview scroll position.
- Status bar breadcrumb for current section.
- Theme manager for built-in and user-imported CSS themes.
- Custom CSS import for screen, code, and print CSS.
- Print controls for page size, margins, content width, heading page breaks, title inclusion, and print theme.
- Export readiness checks for missing links/assets, remote images, rich-content failures, wide tables, and print configuration.
- Snapshot and verifier coverage for inspector and theme states.

### Stretch Scope

- Same-folder references panel showing local Markdown files that link to the current file.
- Link-click popover with open, copy, reveal, and inspect actions.
- Basic CSS validation.
- Source location hints for diagnostics.
- Accessibility/readiness warnings for missing image alt text and heading-level jumps.
- Export with previous PDF/HTML destination.
- Table width warnings for print.

## Architecture Principles

- Keep inspection computation in `OpenMarkedCore`.
- Keep native inspector UI in `OpenMarkedApp`.
- Reuse render diagnostics, document statistics, front matter, link extraction, image extraction, and outline data already produced by the render pipeline.
- Do not parse rendered HTML with ad hoc string scanning where existing extractors can be extended.
- Keep user themes local files or copied local resources, never remote CSS.
- Keep user-authored CSS separate from document-authored HTML/JS.
- Keep print configuration serializable and testable.
- Keep release gates deterministic with fixture-based snapshots and no network dependency.

## Current Architecture Fit

Existing code already has the right foundations:

1. `MarkdownDocument` contains source metadata, front matter, body text, and source statistics.
2. `CMarkGFMRenderer` produces `RenderResult`, outline, diagnostics, statistics, and rich Markdown state.
3. `LinkReferenceExtractor` and link validation already understand local links, fragments, remote links, malformed links, and unsupported schemes.
4. `LocalAssetReferenceExtractor` can find local images from rendered HTML.
5. `DocumentWindowState` already stores current document, render result, layout, live preview, search, and rich-content status.
6. `ContentView` already has outline, preview, diagnostics popover, settings, toolbar, and status bar.
7. `PreviewThemeStore` loads built-in themes and resource CSS.
8. Export/print code already reuses rendered HTML and WebKit.
9. Snapshot and release scripts already gate visual and export behavior.

`0.4.0` should add an inspection layer on top of this rather than creating separate parallel parsing.

## Phase Order

Recommended implementation order:

1. Foundation and inspection models.
2. Inspector shell and state.
3. Front matter and rich statistics.
4. Links, assets, diagnostics, and export readiness.
5. Current section tracking and outline polish.
6. Theme manager and custom CSS import.
7. Print controls.
8. QA, snapshots, docs, and release.

This order makes the first half mostly data and native UI, then moves into theme/import/print behaviors after the inspector has somewhere to display them.

## Open Questions

1. Should the inspector be a right sidebar, a popover, or a detachable utility panel?
2. Should user themes be copied into Application Support or referenced by security-scoped bookmark?
3. Should custom themes support one CSS file only at first, or separate screen/code/print CSS from day one?
4. Should print controls live in Settings, an Export sheet, or both?
5. Should same-folder references/backlinks be included in `0.4.0` or deferred to `0.6.0` folder workflows?
6. How much source-position mapping is acceptable before it becomes too fragile?

## Release Exit Criteria

- Users can open a document and inspect metadata, links, assets, diagnostics, statistics, and export readiness without leaving the preview.
- Users can import and use a local CSS theme safely.
- Users can adjust basic print settings and see those settings reflected in PDF/print output.
- The outline highlights the current section while reading.
- The release remains local-first and offline-capable.
- Automated tests, visual snapshots, export artifacts, package checks, and release verification pass.
