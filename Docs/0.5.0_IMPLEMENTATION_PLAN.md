# OpenMarked 0.5.0 Implementation Plan

## Milestone Summary

OpenMarked `0.5.0` is the Native Tabbed Documents release.

`0.4.x` made OpenMarked a document workbench: rich rendering, inspector, custom themes, print controls, export readiness, and release packaging. `0.5.0` should make working with several Markdown files feel like a native macOS app by opening documents in system window tabs instead of scattering every file into a separate top-level window.

Headline feature:

- Native macOS tabs for Markdown document windows.

Supporting work:

- A documented open-placement policy for single-file, multi-file, drag/drop, Dock, Open Recent, and session-restore flows.
- AppKit window configuration for tab eligibility, tab grouping, and Window menu behavior.
- Command routing that always follows the selected tab's document controller.
- QA coverage for tab creation, tab selection, tab closing, live preview cleanup, export commands, and release packaging.

## Product Goals

1. Make multi-document workflows calmer and more Mac-like.
2. Keep each Markdown file backed by its own `DocumentWindowController`.
3. Preserve existing per-document state: live preview, scroll position, inspector section, outline state, theme, zoom, diagnostics, and export destinations.
4. Use native AppKit tabbing before considering a custom tab strip.
5. Keep Settings, About, open panels, save panels, and help windows outside document tab groups.
6. Keep the feature shippable as a focused `0.5.0` improvement rather than a document-architecture rewrite.

## User Stories

1. As a user opening several Markdown files from File > Open, I see them grouped into tabs in one native window group.
2. As a user opening a file while an empty OpenMarked window is focused, the empty window becomes that document rather than creating an unnecessary tab.
3. As a user opening another file while a document tab is focused, the new document appears as a tab next to the current document.
4. As a user dragging several Markdown files onto an OpenMarked window, the files open as tabs in that window group.
5. As a user using Open Recent or opening files from Finder/Dock, OpenMarked reuses the current document tab group when appropriate.
6. As a user switching tabs, toolbar buttons, menu commands, inspector actions, export, print, search, and source commands operate on the selected tab.
7. As a user closing one tab, only that document's watcher and state close; other tabs keep running.
8. As a user who prefers separate windows, I can use native macOS tab behavior to detach tabs or merge windows.

## Non-Goals

These are intentionally deferred unless they are required to make native tabs correct.

- A custom in-window tab strip.
- A single `NSWindow` with multiple internal document states.
- A multi-document editor surface.
- Folder workspaces, project sidebar, or vault database.
- Tab session restoration beyond reusing the existing last-opened document list.
- Custom tab coloring, pinning, renaming, close buttons, or tab previews.
- Cross-tab search.
- Split panes or side-by-side preview.
- Per-tab unsaved editor state.
- Replacing native Window menu behavior with a custom menu.

## MVP Scope For 0.5.0

### In Scope

- Enable native AppKit tabbing for document windows.
- Give document windows a shared tabbing identifier.
- Set document windows to prefer tabbing where AppKit supports it.
- Open additional supported files as tabs in the active document window group.
- Preserve empty-window replacement behavior for the first file.
- Handle multi-file open, drag/drop, app open events, Dock open events, and session restore.
- Keep command routing tied to the selected tab's `DocumentWindowController`.
- Add user-visible Window menu commands if SwiftUI/AppKit does not expose enough native tab commands automatically.
- Verify tab lifecycle cleanup for file watchers and retained windows.
- Add verifier/test coverage around the open-placement policy and command routing.
- Update README, QA, release notes, and architecture docs for tabbed documents.

### Stretch Scope

- Focus an already-open tab instead of opening the same file twice.
- Add File > Open in New Window or an Option-modified open path.
- Add a setting for "Open new documents in tabs" if native behavior needs a user-facing override.
- Add session restoration that recreates native tab groups rather than only reopening documents.
- Add visual snapshot or Computer Use coverage that records the native tab bar.

## Architecture Principles

- Treat a native tab as an `NSWindow` that belongs to an AppKit tab group.
- Keep the existing one-document-per-controller model.
- Keep document state ownership in `DocumentWindowController`.
- Keep open-placement policy in `AppController`, but make the policy testable with a small pure planner type where possible.
- Avoid putting tab semantics into `OpenMarkedCore`; this is app/window behavior.
- Do not store `NSWindow` strongly inside controllers; continue retaining windows in `AppController`.
- Do not make Settings windows eligible for document tab groups.
- Prefer AppKit APIs for tabs and Window menu commands over SwiftUI-only workarounds when document behavior is native AppKit behavior.

## Current Architecture Fit

OpenMarked already has useful foundations for native tabs:

1. `DocumentWindowController` owns one document's state, rendering, watchers, search, export destinations, and window title.
2. `ContentView` uses a `DocumentWindowController` as its `StateObject`.
3. `AppController.openURLs` already receives a preferred controller and decides whether the preferred controller should be replaced.
4. `AppController.createDocumentWindow(opening:)` already creates one `NSWindow` and one controller per extra file.
5. `WindowAccessor` resolves the `NSWindow` for SwiftUI-created windows.
6. `AppController` observes document `NSWindow` key/main activity and maps it back to the active `DocumentWindowController`.
7. `NSWindow.willCloseNotification` runs `controller.close()` for the closing document and removes document-window registrations.
8. App commands route through `AppController.activeWindowController`.

The main change is the placement policy: when a second document window is created, it should be inserted into the selected document window's native tab group instead of always becoming a separate top-level window.

## Key Design Decisions

### Use Native `NSWindow` Tabbing

Document windows should set:

- `window.tabbingMode = .preferred`
- `window.tabbingIdentifier = "OpenMarkedDocument"`

The app should also enable automatic window tabbing during launch if needed:

- `NSWindow.allowsAutomaticWindowTabbing = true`

Implementation should confirm the exact deployment-target availability and compile behavior on macOS 13.

### Keep Product Version And Tags Separate

The app version for this milestone is `0.5.0`. The Git release tag should be `v0.5.0` to follow the convention established for `v0.4.1`.

### Preserve Empty-Window Replacement

If the active window is empty, opening one or more files should load the first file into that empty window. Remaining files should become tabs in the same tab group.

### Prefer Current Tab Group

When a document tab is focused, additional opens should join that focused tab's tab group. If no document window is focused, use the most recently active document window if it is still alive. If no document window exists, create the first document window normally.

### Do Not Build A Custom Tab UI

The visible tab bar, tab close controls, tab reorder, tab detach, and merge behavior should remain native macOS behavior. OpenMarked should only configure and use it.

## Open Placement Policy

Phase 0 locks the first implementation around a simple native tab policy:

| Entry Point | Preferred Context | First Supported File | Additional Supported Files |
| --- | --- | --- | --- |
| File > Open | Active document controller | Replace an empty active window, otherwise create a tab in the active tab group | Create tabs in the same tab group |
| Toolbar Open | Active document controller | Same as File > Open | Same as File > Open |
| Drag/drop | Drop target controller | Replace an empty drop target, otherwise create a tab in the drop target's tab group | Create tabs in the same tab group |
| Finder/Dock open events | Active or most recent document controller | Replace an empty document window, otherwise create or join the current tab group | Create tabs in the same tab group |
| Open Recent | Active or most recent document controller | Same as Finder/Dock open events | Not applicable for a single recent item |
| Session restore | Initial document window if present | Replace the initial empty window | Create tabs in the same tab group |

If no document window exists, OpenMarked creates the first document window as a standalone native document window and then uses that window as the tab anchor for any remaining files.

Duplicate-document focusing is stretch scope for `0.5.0`. Until it lands, opening the same file twice may create a second tab for the same source document.

## Proposed Open Placement Model

Suggested app-only model:

```swift
enum DocumentOpenPlacement: Equatable {
    case replace(DocumentWindowController)
    case newStandaloneWindow
    case newTab(in: DocumentWindowController)
}
```

Because `DocumentWindowController` is not value-equatable, tests may use a pure planner with lightweight window descriptors:

```swift
struct DocumentWindowDescriptor: Equatable {
    var id: UUID
    var isEmpty: Bool
    var isAlive: Bool
    var isActive: Bool
}

enum PlannedDocumentOpenPlacement: Equatable {
    case replace(UUID)
    case newStandaloneWindow
    case newTab(anchor: UUID)
}
```

The production controller can map the planner's result back to actual controllers and windows.

## Proposed AppKit Helpers

Suggested files:

- `Sources/OpenMarkedApp/DocumentWindowTabbing.swift`
- `Sources/OpenMarkedApp/DocumentOpenPlacementPlanner.swift`

Candidate helpers:

```swift
enum DocumentWindowTabbing {
    static let identifier = "OpenMarkedDocument"

    static func configureDocumentWindow(_ window: NSWindow) {
        window.tabbingIdentifier = identifier
        window.tabbingMode = .preferred
    }

    static func addWindow(_ window: NSWindow, asTabTo anchorWindow: NSWindow) {
        anchorWindow.addTabbedWindow(window, ordered: .above)
    }
}
```

Exact API calls should be validated during implementation. If AppKit ordering or focus behavior differs from expectation, adapt through a tiny helper and keep call sites simple.

## Phase Order

Recommended implementation order:

1. Planning and tabbing foundation.
2. Native tabbed window creation.
3. Open routing for all document entry points.
4. Active-tab command routing and lifecycle cleanup.
5. Menu integration, shortcuts, and accessibility.
6. Session restore and duplicate handling polish.
7. QA, docs, packaging, and release.

This order keeps the first implementation focused on AppKit plumbing, then broadens to user workflows and verification.

## Release Exit Criteria

`0.5.0` is ready to release when:

- File > Open with multiple files opens native tabs.
- Drag/drop with multiple files opens native tabs.
- Dock/Finder open events use the tab policy when OpenMarked is already running.
- Empty windows are reused for the first document.
- Commands always target the selected tab.
- Closing a tab cleans up that tab's watcher and retained window state.
- Per-document settings and export destinations remain independent across tabs.
- Window menu tab commands are available or documented.
- `swift build` passes.
- `swift test` passes.
- `swift run OpenMarkedVerifier` passes.
- `Scripts/verify_release.sh` passes.
- Manual macOS tab QA is recorded.
- README, QA, release notes, and architecture docs are updated.

## Risks And Mitigations

### Risk: Native Tab Selection Does Not Emit Expected Notifications

Mitigation:

- Test `didBecomeKey` and `didBecomeMain` behavior with native tabs.
- Add delegate callbacks if notification observation is insufficient.
- Keep command routing checks in manual QA.

### Risk: AppKit Tabbing Behavior Differs Between SwiftUI And Programmatic Windows

Mitigation:

- Configure both WindowGroup-created and programmatically-created document windows through the same helper.
- Use `WindowAccessor` for SwiftUI-created windows.
- Keep Settings windows out of the helper.

### Risk: Closing A Tab Leaks Watchers Or Retained Windows

Mitigation:

- Confirm `windowWillClose` fires for native tab close.
- Add retained-window count/debug assertions where practical.
- Exercise close flows in manual QA.

### Risk: Multiple Open Entry Points Drift Apart

Mitigation:

- Route File > Open, drop, Dock/Finder open, Open Recent, and session restore through the same `openURLs` policy.
- Keep bypasses only for explicit "Open in New Window" stretch behavior.

### Risk: Exact Tab Restoration Becomes Too Big

Mitigation:

- Reuse existing last-opened document restoration first.
- Defer exact tab order/group restoration unless the native API makes it straightforward.
