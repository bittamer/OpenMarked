# OpenMarked 0.5.1 Performance Audit And Plan

This audit focuses on lag while scrolling very large Markdown notes with many images.

## Summary

Large image-heavy notes currently stress both the preview WebView and OpenMarked's native SwiftUI shell. The biggest observed issue is not Markdown parsing itself. It is repeated main-thread work triggered while the preview is loading or scrolling:

- Status bar statistics are recalculated from the full Markdown source during SwiftUI view updates.
- Built-in preview themes are reloaded from bundled CSS more often than needed.
- The injected current-section tracker scans headings during scroll and posts updates back to SwiftUI.
- Image-heavy documents create many local asset watchers and can force WebKit to decode/layout many full-size images.
- The inspector rebuilds rich inspection reports synchronously when visible, including local image metadata probes.
- SwiftUI/AppKit bridge helpers must avoid repeated no-op native window writes, because those can keep the native shell relayouting after the preview has gone idle.

The recommended path is a short performance stabilization release that first removes repeated native work during scroll, then improves image loading and asset watching.

## Implementation Status

Status: implemented for `0.5.1`.

- Phase 0: generated large-image fixture script, repeatable scroll audit script, and synthetic performance smoke fixtures are in place.
- Phase 1: built-in preview themes and status-bar statistics are cached, and current-section native updates are guarded and debounced.
- Phase 2: preview section tracking caches heading offsets, uses throttled lookup, and applies automatic large-document fallbacks.
- Phase 3: rendered images receive lazy/async hints and local dimensions, metadata is cached by file signature, and preview-only oversized raster downsampling is available while export/print keep originals.
- Phase 4: referenced local image watching now chooses per-file, directory-filtered, or manual reload strategies with a shared debounce and visible status hints.
- Phase 5: document inspection reports are stored after render, asset metadata reads use the shared cache, and long inspector lists are lazy-capped with Show All controls.
- Phase 6: document loading, rendering, postprocessing, and inspection report generation run in cancellable background tasks; stale load/render results are suppressed.
- Phase 7: Settings exposes Performance Mode, Current Section tracking, and Referenced Images reload behavior, with documentation and release metadata updated for `0.5.1`.
- Final audit addendum: `WindowAccessor`, active-window routing, and window chrome background writes are idempotent, fixing a native SwiftUI layout feedback loop discovered during post-settle sampling.

## Audit Method

Temporary fixture:

- Generated under `.build/perf-audit/large-images.md`.
- 480 Markdown image references.
- 40 local PNG files generated from the SVG fixture at 2400 by 2400.
- Total temporary audit data: about 12 MB.

Runtime check:

- App: `dist/OpenMarked-0.5.0/OpenMarked.app`.
- macOS: 26.5.1.
- Opened the synthetic large-image document.
- Sent repeated Page Down events through System Events.
- Sampled scroll-time CPU/RSS and stacks, then waited for a post-scroll settle window and sampled idle CPU/RSS and stacks.

Observed behavior:

- OpenMarked main process reached roughly 95-100% CPU during initial heavy preview activity and early scrolling.
- RSS rose from roughly 163 MB to 185 MB on the synthetic fixture.
- A 3-second `sample` run showed repeated main-thread SwiftUI work in `StatusBar.body`, `StatusBar.currentStatistics`, `DocumentStatisticsCalculator.calculate`, and `PreviewThemeStore` theme lookup/loading.
- In this fixture, WebKit helper processes were comparatively quiet, which suggests the native shell is currently adding avoidable pressure even before deeper WebKit image optimizations.

## Findings

### P0: Status Bar Recalculates Full Statistics During Scroll

Current code:

- `ContentView.swift`
- `StatusBar.currentStatistics`
- `DocumentStatisticsCalculator.calculate(document:options:)`

The status bar recomputes word count, character count, line count, and reading time from the document text inside a SwiftUI computed property. When scroll-driven state changes invalidate the view tree, this can rerun the full localized word tokenizer repeatedly.

Impact:

- Direct main-thread CPU during scroll.
- Scales with document text size.
- Easy to fix without changing preview behavior.

Recommendation:

- Store the default document statistics already computed during load.
- Add a cached settings-aware statistics value for the status bar when `includesFrontMatterInStatistics` or WPM differs from the loaded default.
- Recompute only when the document changes or statistics settings change.

### P0: Preview Theme Lookup Reloads Bundled CSS Repeatedly

Current code:

- `PreviewThemeStore.allBuiltInThemes`
- `PreviewThemeStore.builtInTheme(id:)`
- `PreviewThemeStore.loadCSS(named:fallback:)`
- `AppController.previewTheme(id:)`

Theme lookup currently constructs themes by reading bundled CSS. The status bar and toolbar can ask for the active theme while views update.

Impact:

- Avoidable file/resource lookup in UI updates.
- Visible in sampling during the large-image scroll audit.

Recommendation:

- Cache built-in `PreviewTheme` values statically.
- Cache built-in IDs as a static `Set<String>`.
- Ensure `AppController.availablePreviewThemes` and `previewTheme(id:)` do not trigger CSS file reads after startup.

### P0: Current Section Updates Can Repaint Native UI During Scroll

Current code:

- `PreviewWebView.installPreviewHelpers`
- `openMarkedSectionTracker.schedule`
- `DocumentWindowController.updateCurrentPreviewSection`
- `DocumentWindowState.updateCurrentSection`
- `OutlineSidebar` and `StatusBar`

The preview injects a scroll listener that schedules current-heading detection. It queries all headings and uses `getBoundingClientRect` while scrolling. When it posts a section change, SwiftUI updates the outline and status bar.

Impact:

- Repeated DOM measurement during scroll.
- Repeated native state updates and view invalidation.
- More costly when the document has many headings, or when the outline/status/inspector are visible.

Recommendation:

- Add a same-value guard in `updateCurrentSection`.
- Debounce native current-section updates to roughly 150-250 ms.
- Cache the heading list once after load instead of running `querySelectorAll` on each scheduled check.
- Consider `IntersectionObserver` or an offset cache with binary search for large documents.
- Disable current-section tracking automatically in performance mode or above a large-document threshold.

### P1: Images Are Loaded At Source Size

Current theme CSS:

- Most themes use `img { max-width: 100%; height: auto; border-radius: 6px; }`.

Rendered HTML does not currently add image loading hints, intrinsic dimensions, or preview-specific downsampled sources.

Impact:

- WebKit may decode very large local images even when displayed at document width.
- Missing `width` and `height` can increase layout work and scroll-position instability as images resolve.
- Many images make initial preview load and first scroll expensive.

Recommendation:

- Add an image postprocessor in the render pipeline that preserves existing attributes and adds:
  - `loading="lazy"` when absent.
  - `decoding="async"` when absent.
  - `width` and `height` for local images when cached metadata is available.
- Add a preview image cache:
  - Downsample local raster images wider than the preview max width.
  - Use `CGImageSourceCreateThumbnailAtIndex`.
  - Cache by source path, file size, mtime, pixel dimensions, theme max width, and scale factor.
  - Use originals for export and print unless the user explicitly requests optimized export.
- Keep SVGs as originals unless a later renderer-specific need appears.

### P1: One Watcher Per Image Does Not Scale

Current code:

- `DocumentWindowController.updateAssetWatchers`.
- One `FileSystemWatcher` is created for each distinct local image URL.

Impact:

- Hundreds of image references can create many dispatch sources.
- Re-rendering updates the watcher set, adding churn.
- Asset changes can force full document reload.

Recommendation:

- Add a watcher strategy:
  - For small documents, keep per-file image watching.
  - Above a threshold, watch parent directories and filter events against the referenced asset set.
  - Above a higher threshold, disable asset watching by default and show "manual reload recommended" in status/inspector.
- Coalesce asset events across all watchers with a single document-level debounce.
- Add a setting for "Live reload referenced images" with an automatic/default mode.

### P1: Inspector Builds Are Synchronous And Repeated

Current code:

- `InspectorSidebar.currentInspectionReport`.
- `DocumentInspectionBuilder.build`.
- `assetFileInfo(for:)` and `imageDimensions(for:)`.

The inspector builds reports from scratch inside a SwiftUI computed property. For image-heavy notes, this can include many file attribute reads and ImageIO dimension probes.

Impact:

- Main-thread CPU when inspector is visible.
- Repeated work if SwiftUI invalidates the inspector.
- Asset and link rows are rendered in regular `VStack` containers, which do not virtualize large lists.

Recommendation:

- Build `DocumentInspectionReport` once per render and store it in `DocumentWindowState`.
- Move expensive asset metadata reads to a background task with a cache.
- Use `LazyVStack` or `List` for long inspector sections.
- Add display limits with "show all" affordances for thousands of links/assets/diagnostics.

### P2: Rendering And Inspection Run On The Main Actor

Current code:

- `DocumentWindowController.render`.
- `CMarkGFMRenderer.render`.
- postprocessors and diagnostics collection.

The controller is `@MainActor`, so rendering, regex postprocessing, diagnostics, and watcher updates are initiated from the main actor.

Impact:

- Large saves/reloads can block the UI.
- Regex postprocessors and link/image diagnostics scale with HTML size.

Recommendation:

- Move Markdown load/render/inspection to a background task.
- Publish only state transitions and final `RenderResult` on the main actor.
- Add cancellation so rapid live-preview saves do not queue obsolete renders.

### P2: Full HTML Reload Remains Expensive

Current code:

- `PreviewWebView.Coordinator.load`.
- `WKWebView.loadHTMLString`.

The WebView reload guard avoids identical HTML reloads, which is good. But any render-changing edit, theme change, zoom change, content setting, or asset change still reloads the full HTML document.

Impact:

- WebKit rebuilds the whole DOM.
- Image-heavy notes repeat decode/layout work.

Recommendation:

- Keep full reload for correctness in the near term.
- After the P0/P1 fixes, evaluate DOM patching only for live-preview text edits.
- Defer DOM diffing until after image lazy loading, stats caching, and theme caching are complete.

## Implementation Plan

### Phase 0: Measurement Foundation

Tickets:

- PERF-000: Add a generated large-image fixture helper under `Scripts/` or `Tests/Fixtures`.
- PERF-001: Add a repeatable scroll audit script that opens the packaged app, scrolls a fixture, records CPU/RSS, and saves a `sample` report.
- PERF-002: Add lightweight render timing for large text, many images, many headings, and many links.
- PERF-003: Define initial budgets:
  - App idle CPU below 5% after initial load settles.
  - No repeated word-count calculation while scrolling.
  - No repeated CSS resource reads while scrolling.
  - 500-image fixture scroll remains responsive after initial image decode.

### Phase 1: Native Main-Thread Hotfixes

Tickets:

- PERF-100: Cache built-in preview themes and theme IDs in `PreviewThemeStore`.
- PERF-101: Replace status-bar `currentStatistics` recalculation with cached document statistics.
- PERF-102: Add settings-aware cached statistics for alternate WPM/front-matter settings.
- PERF-103: Guard `DocumentWindowState.updateCurrentSection` against no-op updates.
- PERF-104: Debounce `DocumentWindowController.updateCurrentPreviewSection`.
- PERF-105: Add tests proving status bar stats and theme lookup do not perform repeated expensive work.

Expected result:

- Large-image scroll no longer spends app-process CPU on word counting or CSS loading.
- Native UI invalidation from current-section updates is reduced.

### Phase 2: Scroll Tracker Optimization

Tickets:

- PERF-200: Cache heading elements once in the injected preview helper after each document load.
- PERF-201: Replace per-scroll heading scans with an offset cache plus binary search, or `IntersectionObserver` where reliable.
- PERF-202: Increase scroll tracker throttle for large documents.
- PERF-203: Disable current-section tracking when outline and status section display are both hidden.
- PERF-204: Add a large-document fallback that turns current-section tracking into idle-only updates.

Expected result:

- Scrolling no longer causes repeated full heading scans or frequent native state posts.

### Phase 3: Image Loading Optimization

Tickets:

- PERF-300: Add an image attribute postprocessor that injects `loading="lazy"` and `decoding="async"` without clobbering author HTML.
- PERF-301: Build a local image metadata cache keyed by path, file size, mtime, and file ID.
- PERF-302: Add intrinsic `width` and `height` attributes for local raster/SVG images when known.
- PERF-303: Add preview-only raster downsampling for oversized local images.
- PERF-304: Add cache eviction and corruption recovery for generated preview images.
- PERF-305: Keep export and print on original assets by default.

Expected result:

- Initial image-heavy preview load and first scroll become substantially smoother.
- Scroll position is more stable because image dimensions are known earlier.

### Phase 4: Asset Watcher Scaling

Tickets:

- PERF-400: Introduce `AssetWatchStrategy` with `.perFile`, `.directoryFiltered`, and `.manualReload`.
- PERF-401: Switch to directory-filtered watching above a configurable asset count.
- PERF-402: Add one shared document-level debounce for all asset change events.
- PERF-403: Surface asset watching mode in the status bar or inspector for very large documents.
- PERF-404: Add tests for watcher strategy selection and coalescing.

Expected result:

- Hundreds of local images do not create hundreds of active watcher pipelines.

### Phase 5: Inspector Performance

Tickets:

- PERF-500: Store inspection reports in state after render instead of rebuilding in SwiftUI computed properties.
- PERF-501: Move asset file info and image dimensions to a background metadata task.
- PERF-502: Cache asset metadata by file signature.
- PERF-503: Use lazy/virtualized containers for links, assets, diagnostics, and section statistics.
- PERF-504: Add large-list limits with explicit "show all" controls.

Expected result:

- Opening the inspector on a large image note does not pause scrolling or spike main-thread CPU.

### Phase 6: Background Rendering

Tickets:

- PERF-600: Move Markdown load/render/postprocess work off the main actor.
- PERF-601: Add render cancellation when a newer live-preview event arrives.
- PERF-602: Keep state mutation, alerts, and WebView loading on the main actor.
- PERF-603: Add tests for cancellation and stale render suppression.

Expected result:

- Large save/reload operations do not freeze the app shell.

### Phase 7: User Controls And Safe Fallbacks

Tickets:

- PERF-700: Add a Performance Mode setting with automatic/default behavior.
- PERF-701: Add settings for current-section tracking and referenced-image live reload.
- PERF-702: Add a large-document banner or status hint when OpenMarked chooses degraded-but-smooth behavior.
- PERF-703: Document performance behavior in README and QA docs.

Expected result:

- Users with very large notes get predictable behavior and can choose fidelity versus speed.

## Recommended Release Scope

For a quick `0.5.1`, ship Phases 0-2 plus the lowest-risk part of Phase 3:

- Measurement fixture/script.
- Theme cache.
- Cached status-bar statistics.
- No-op guard and debounce for current section.
- Cached heading list in the WebView helper.
- `loading="lazy"` and `decoding="async"` on rendered images.

For `0.6.0`, ship:

- Preview image downsampling cache.
- Asset watcher scaling.
- Cached/background inspector reports.
- Background rendering and cancellation.
