# OpenMarked 0.5.2 Performance Optimisation Implementation Plan

Status: Phase 0 complete; optimisation phases planned

Version: `0.5.2`

Primary rule: optimise for performance first. Prefer removing repeated work and duplicate code paths over adding new abstractions. Less code is better than more when behavior stays the same.

## Summary

OpenMarked `0.5.1` fixed the most visible large-document scroll lag by caching status statistics, caching built-in preview themes, scaling image watchers, lazy-capping inspector lists, and moving rendering work off the main actor.

`0.5.2` should go deeper. The app still performs many identical scans, regex passes, disk reads, file stats, and UI metadata conversions across independent modules. The largest opportunity is to make rendering produce one reusable analysis model, then feed that model into diagnostics, inspection, performance profiles, asset watchers, preview image handling, export, and security filtering.

The target result is the same user-visible behavior with:

- Fewer full-document scans per render.
- Fewer file and bundle reads during render and SwiftUI updates.
- No full Markdown render just to validate headings in linked documents.
- Less SwiftUI allocation churn during normal view invalidation.
- Smaller source files by deleting duplicate extractors, duplicate display metadata, and duplicate tests.
- Stronger raw HTML safety without adding another independent sanitizer pass.

## Release Goals

1. Preserve the `0.5.1` behavior baseline.
2. Reduce repeated render pipeline work.
3. Reduce main-thread work during SwiftUI view updates.
4. Reduce disk I/O during render, theme lookup, and state persistence.
5. Improve raw HTML safety in the preview and export path.
6. Remove duplicate extractor, parser, display, and test code.
7. Keep the implementation incremental enough that each phase can be verified independently.

## Non-Goals

- No visual redesign.
- No new user-facing feature scope unless it is required to preserve existing behavior.
- No replacement of `cmark-gfm`.
- No custom DOM implementation.
- No broad architecture rewrite of `DocumentWindowController`.
- No cache that can return stale file content after a file changes.
- No performance mode behavior changes beyond preserving the current automatic fallbacks.

## Acceptance Criteria

Every phase must keep:

- `swift test` passing.
- `swift run OpenMarkedVerifier` passing.
- Existing visual QA fixtures rendering equivalently where snapshots are part of the touched behavior.
- Export HTML preserving original image sources unless the user explicitly chooses an optimized export path.
- Preview HTML preserving existing safe behavior while blocking additional unsafe raw HTML cases.

Performance acceptance targets:

- Link, image, code-block, asset, and count extraction should come from one render analysis pass instead of scattered full-string scans.
- Cross-document heading validation must not call `CMarkGFMRenderer.render`.
- Built-in rich content resources must be read from the bundle once per process.
- Built-in app chrome themes must be built once per process.
- User preview themes must not be reread from disk during ordinary SwiftUI body updates when their files have not changed.
- Repeated Find Next or Find Previous in the preview must not re-highlight the entire document when the query has not changed.
- Window state saves must not decode the entire persisted state dictionary on every layout write.

Line-count acceptance targets:

- Net product source should decrease after phases 2 through 5.
- Any new helper must delete at least one existing duplicate code path in the same phase.
- Test cleanup should remove the duplicated XCTest/Swift Testing suites after parity is proven.

## Implementation Order

The safest order is:

1. Phase 0: lock behavior and add minimal measurements.
2. Phase 1: cache-only and lazy UI wins.
3. Phase 2: shared rendered HTML index and sanitizer.
4. Phase 3: heading-only cross-document validation and Markdown scanner reuse.
5. Phase 4: preview helper JavaScript extraction and search reuse.
6. Phase 5: state persistence, watcher cleanup, and test-suite deduplication.
7. Phase 6: final performance audit and release notes.

This order takes low-risk performance wins first, then removes the largest duplicated parsing paths once the baseline is protected.

## Priority 1: Shared Rendered HTML Index

### Current Cost

The same rendered HTML is scanned repeatedly by independent modules:

- Render result assembly counts images and links.
- Link diagnostics extract anchors.
- Local asset watchers extract image URLs.
- Image attribute processing scans image tags.
- Preview image optimization scans image tags again.
- Document inspection extracts links and images.
- Export scans images for embedding.
- Security sanitization scans unsafe tags and attributes separately.

This creates extra CPU and more code. It also makes safety behavior harder to reason about because every extractor owns its own partial HTML parsing rules.

### Implementation

Create one small core utility, preferably in `Sources/OpenMarkedCore/RenderedHTMLIndex.swift`.

Suggested types:

```swift
public struct RenderedHTMLIndex: Equatable, Sendable {
    public var links: [RenderedLinkReference]
    public var images: [RenderedImageReference]
    public var codeBlocks: [RenderedCodeBlockReference]
    public var tableCount: Int
    public var localImageURLsBySource: [String: URL]
}
```

Keep the model narrow. Do not build a general DOM.

Add a compact internal scanner:

- Finds start tags.
- Handles single-quoted, double-quoted, and unquoted attributes.
- Preserves original tag ranges for rewriting.
- Decodes only where existing behavior requires decoded URLs or text.
- Treats malformed HTML conservatively and continues scanning.

Then replace duplicate callers:

1. Replace `LinkReferenceExtractor.linkReferences(from:)` internals with the new index.
2. Replace `LocalAssetReferenceExtractor.imageURLs` and `localImageSources` internals with the new index.
3. Replace `DocumentInspectionBuilder.buildLinks` and `buildAssets` with index data.
4. Replace render-time `linkCount` and `imageCount` with index counts.
5. Feed `updateAssetWatchers` from the render result analysis instead of rescanning body HTML.
6. Let image attribute processing and preview image optimization share one tag rewriting helper.
7. Keep compatibility wrappers temporarily only if they reduce churn; delete them once all call sites move.

### Data Flow

Target render flow:

1. `CMarkGFMRenderer` produces body HTML.
2. Postprocessors update body HTML.
3. `RenderedHTMLIndex.build` runs once on final body HTML.
4. Diagnostics, inspection, performance profile, asset watchers, and preview image optimization reuse the index.
5. Export uses original full HTML plus the index where possible, preserving original image sources.

### Files

Primary:

- `Sources/OpenMarkedCore/MarkdownRendering.swift`
- `Sources/OpenMarkedCore/DocumentInspection.swift`
- `Sources/OpenMarkedCore/LinkValidation.swift`
- `Sources/OpenMarkedCore/ImagePerformance.swift`
- `Sources/OpenMarkedCore/HTMLExporting.swift`
- `Sources/OpenMarkedApp/DocumentWindowController.swift`

New or replacement:

- `Sources/OpenMarkedCore/RenderedHTMLIndex.swift`

### Deletion Targets

Delete or collapse most of:

- Regex-only anchor extraction.
- Regex-only local image extraction.
- Duplicate image attribute parsing.
- Duplicate image source resolution.
- Per-call image count via string splitting.
- Per-diagnostic `diagnostics.filter` loops in inspection.

### Performance Target

For a normal rich render, reduce repeated whole-HTML extraction passes from many independent scans to one index build plus the unavoidable postprocessor rewrites.

### LOC Target

The new scanner should be smaller than the extractors it replaces. Net product source should decrease after all call sites are migrated.

### Tests

Add or update tests for:

- Double-quoted attributes.
- Single-quoted attributes.
- Unquoted attributes.
- Attributes containing escaped entities.
- Fragment links.
- Relative file links.
- Local image URLs.
- Remote images.
- Data image URLs if currently accepted.
- Malformed tags that should not crash extraction.

## Priority 2: Heading-Only Cross-Document Validation

### Current Cost

Cross-document heading validation renders target Markdown documents just to discover headings. That means link validation can invoke the full Markdown renderer, postprocessors, diagnostics, and HTML assembly for target documents.

This is the wrong amount of work for a heading existence check.

### Implementation

Add a heading-only scanner, preferably shared with document title extraction and outline-related helpers.

Suggested type:

```swift
struct MarkdownHeadingIndex: Sendable {
    var headings: [MarkdownHeading]
    var headingsBySlug: Set<String>
    var firstHeadingTitle: String?
}
```

Suggested cache:

```swift
struct LinkValidationContext {
    var headingCache: [FileSignature: MarkdownHeadingIndex]
}
```

Steps:

1. Create `MarkdownHeadingScanner` using the same heading rules and slug generation already used after rendering.
2. Add `FileSignature` with path, size, and modification date.
3. During one document render, cache every target file's heading index by signature.
4. Replace the target-document `CMarkGFMRenderer.render` call with `MarkdownHeadingScanner.scan`.
5. Keep the current fallback diagnostics for missing files, unreadable files, directories, and unsupported schemes.
6. Avoid caching across process lifetime unless there is a clear invalidation path. A per-render cache is enough and safer.

### Files

Primary:

- `Sources/OpenMarkedCore/LinkValidation.swift`
- `Sources/OpenMarkedCore/MarkdownDocument.swift`
- `Sources/OpenMarkedCore/MarkdownRendering.swift`

New:

- `Sources/OpenMarkedCore/MarkdownHeadingScanner.swift`

### Deletion Targets

- Full renderer invocation inside cross-document heading validation.
- Duplicate first-heading parsing code.
- Duplicate Markdown heading parsing in inspection.

### Performance Target

Validating many links to the same target file should read and scan that target once, not render it repeatedly.

### LOC Target

The scanner must replace existing heading resolver/parser code, not sit beside it indefinitely.

### Tests

Add tests for:

- Existing cross-document heading links still pass.
- Missing heading links still warn.
- Repeated links to the same file use a cached heading index.
- Heading slug behavior matches current rendered heading IDs.
- Front matter does not become a heading.
- Fenced code headings do not count.

## Priority 3: Rich Asset And User Theme Caches

### Current Cost

Rich content CSS and JavaScript resources are read from the bundle and transformed repeatedly. User preview themes can be reread from disk during ordinary UI updates through theme lookup.

This is avoidable disk and bundle work.

### Implementation

#### Rich Content Assets

In `RichContentAssetStore`:

1. Cache each resource string in a static, thread-safe value.
2. Cache transformed KaTeX CSS after font URL replacement.
3. Cache runtime script arrays by requested `RichMarkdownRenderState`.
4. Keep throwing behavior for missing required resources.

Prefer static `let` or small static dictionaries initialized once. Avoid adding a large custom cache type.

#### User Preview Themes

In `UserPreviewThemeStore`:

1. Cache `PreviewTheme` by user theme ID and file signature.
2. Invalidate the entry on import, rename, delete, or when the file signature changes.
3. Make `AppController.availablePreviewThemes` return cached theme values.
4. Ensure the status bar and toolbar do not trigger disk reads when displaying the current theme name.

### Files

Primary:

- `Sources/OpenMarkedCore/RichContentAssets.swift`
- `Sources/OpenMarkedCore/RichContentWebViewRuntime.swift`
- `Sources/OpenMarkedCore/HTMLExporting.swift`
- `Sources/OpenMarkedCore/ThemeManagement.swift`
- `Sources/OpenMarkedApp/AppController.swift`
- `Sources/OpenMarkedApp/ContentView.swift`

### Deletion Targets

- Repeated resource-string loading helpers where a cached static value can replace them.
- Repeated user-theme CSS validation from view lookups.
- Any separate theme-name lookup that can reuse the cached `PreviewTheme`.

### Performance Target

- Built-in rich resource files are read once per process.
- A user theme file is read only when imported, changed, or first requested after cache invalidation.

### LOC Target

The cache should be smaller than the repeated read/transform logic it replaces.

### Tests

Add tests for:

- Rich runtime scripts still return the same script count and content ordering.
- KaTeX CSS still has package resource font URLs.
- Unsafe user CSS still falls back to the default theme.
- Edited user CSS invalidates by file signature.
- Theme lookup from `AppController` does not perform repeated file reads when unchanged. Use a small injected reader if needed.

## Priority 4: Stronger Preview HTML Sanitization

### Current Cost And Risk

The sanitizer removes script blocks and quoted event handler attributes, but raw HTML can also express unsafe behavior through unquoted event handlers or dangerous URL schemes.

This is a safety problem. It is also duplicated parsing work if the sanitizer remains a separate regex-only pass.

### Implementation

Fold sanitization into the shared HTML scanner from Priority 1.

Rules:

1. Remove `<script>` blocks.
2. Remove event handler attributes whose lowercased names start with `on`, regardless of quoting style.
3. Remove dangerous URL values from `href`, `src`, `xlink:href`, `formaction`, and similar URL-bearing attributes.
4. Allow current safe URL behavior:
   - Fragment links.
   - Relative links.
   - `http` and `https`.
   - `mailto`.
   - Local file links where already supported.
   - `data:image/*` only if current behavior requires it.
5. Block at least:
   - `javascript:`
   - `vbscript:`
   - `data:text/html`
   - Control-character-obfuscated schemes.

Keep the sanitizer conservative. If behavior is uncertain, add a test that captures current desired behavior before changing it.

### Files

Primary:

- `Sources/OpenMarkedCore/MarkdownRendering.swift`
- `Sources/OpenMarkedCore/HTMLExporting.swift`

Potential new home:

- `Sources/OpenMarkedCore/HTMLSanitizer.swift`

### Deletion Targets

- Regex-only sanitizer rules after the scanner-backed sanitizer lands.
- Duplicate attribute parsing used only for security checks.

### Performance Target

Security filtering should reuse scanner-backed tag parsing and should not add a new full HTML pass beyond the index/rewrite work already needed for render.

### Tests

Add tests for:

- `<script>` removal.
- Double-quoted event handler removal.
- Single-quoted event handler removal.
- Unquoted event handler removal.
- Mixed-case event handler removal.
- `javascript:` links.
- Whitespace/control-obfuscated dangerous schemes.
- Safe fragment, relative, HTTP, HTTPS, and mailto links.

## Priority 5: Document Title, Front Matter, And Markdown Scanner Reuse

### Current Cost

The document first heading is computed by rescanning body text when accessed. Front matter parsing tries multiple delimiter paths and splits full source text. Heading parsing is duplicated across title resolution and inspection.

### Implementation

1. Add stored heading metadata to `MarkdownDocument`, with default initializer values to keep tests simple:

   ```swift
   public let firstHeadingTitle: String?
   ```

2. Compute heading metadata in `MarkdownDocumentLoader.load` after front matter parsing.
3. Make `resolvedTitle` and `resolvedTitleSource` use stored metadata.
4. Replace duplicate heading parsing in inspection with `MarkdownHeadingScanner`.
5. Refactor `FrontMatterParser.parse`:
   - Read only the first line to select a delimiter.
   - If there is no matching opening delimiter, return immediately.
   - Find the closing delimiter without splitting the entire document into arrays for every possible format.
   - Preserve existing YAML, TOML, and JSON delimiter behavior.

### Files

Primary:

- `Sources/OpenMarkedCore/MarkdownDocument.swift`
- `Sources/OpenMarkedCore/DocumentInspection.swift`
- `Sources/OpenMarkedCore/RichMarkdown.swift`

### Deletion Targets

- `MarkdownDocumentTitleResolver` duplicate scanner.
- Inspection-only Markdown heading parser.
- Repeated front matter split attempts.

### Performance Target

Title and first-heading access should be O(1) after document load.

### LOC Target

Net code should decrease by replacing three heading parsers/resolvers with one scanner.

### Tests

Add or update tests for:

- Title from front matter still wins.
- First heading title still resolves when no front matter title exists.

## Priority 7: Preview Helper JavaScript Extraction And Search Reuse

### Current Cost

`PreviewWebView` embeds a large helper JavaScript string in Swift. Search actions clear and re-highlight the whole preview even when the user only asks for next or previous with the same query.

### Implementation

1. Move helper JavaScript into a resource file:

   - Option A: add resources to the `OpenMarkedApp` target.
   - Option B: store the helper in `OpenMarkedCore/Resources` if reusing the existing resource setup is smaller.

   Prefer the option with the least package and loader code.

2. Cache the helper script string once.
3. Replace manual Swift string interpolation for query/id values with JSON serialization for JavaScript string literals.
4. Update the JS search helper:
   - Keep current query, match list, and selected index.
   - For `next` or `previous` with the same query, move the active class and scroll only.
   - Only clear and re-highlight when the query changes, the document reloads, or search is cleared.
5. Ensure section tracking behavior changes apply without a full preview reload when settings change.

### Files

Primary:

- `Sources/OpenMarkedApp/PreviewWebView.swift`
- `Package.swift` if app resources are added.

Potential new:

### Deletion Targets

- Large embedded JavaScript string from Swift.
- `PreviewJavaScriptEscaper` if JSON serialization replaces it.
- Duplicate query clear/re-highlight logic in JS.

### Performance Target

Find Next and Find Previous should not rescan and rewrite the entire preview DOM for an unchanged search query.

### LOC Target

Swift source should shrink substantially. JS should be easier to read but not grow feature scope.

### Tests

## Priority 9: Window State Persistence Efficiency

### Current Cost

Every window state save reloads and rewrites the full persisted dictionary. Layout, theme, zoom, export destination, and inspector toggles can call this often.

### Implementation

1. Make `DocumentWindowStateStore` load persisted state once into an in-memory dictionary.
2. Keep writes serialized through the existing lock or a small serial queue.
3. On `save`, update the cached dictionary directly.
4. Persist the encoded dictionary without first decoding it again.
5. Consider a short debounce only if repeated writes remain visible after the cache lands.
6. Preserve the existing `UserDefaults` key and JSON format.
7. Flush synchronously on close if a debounce is introduced.

Prefer the in-memory cache first. It gives most of the win with less code and less crash-recovery risk than an aggressive delayed writer.

### Files

Primary:

- `Sources/OpenMarkedCore/DocumentWindowStateStore.swift`
- `Sources/OpenMarkedApp/DocumentWindowController.swift`

### Deletion Targets

- Per-save `loadAll`.
- Repeated decode/encode round trips for unchanged persisted entries.

### Performance Target

State persistence should be O(1) in memory plus one encode/write, not decode plus encode on every state update.

### LOC Target

The store should become simpler: one loaded cache, one save path, one restore path.

### Tests

Add or update tests for:

- Save then restore still works.
- Multiple document states survive.
- Updating one document does not remove another.
- Store handles corrupted persisted data by falling back safely.
- Close/flush preserves the last state if debouncing is added.

## Priority 10: Test Suite Deduplication

### Current Cost

The core and app tests duplicate many scenarios across XCTest and Swift Testing. This increases maintenance cost and makes refactors slower because every behavior update has to be applied twice.

This is not a runtime performance change, but it improves implementation velocity and lowers the risk of missing a behavior assertion during the optimisation work.

### Implementation

1. Choose one default framework for each target.
2. Prefer the framework that yields less code for the same coverage.
3. Keep XCTest only where `XCTestCase` lifecycle or AppKit integration makes it materially simpler.
4. Before deleting a duplicate block, create a parity checklist:
   - Assertion exists in kept suite.
   - Failure message remains useful.
   - Setup/teardown behavior remains covered.
5. Delete duplicate scenarios after parity is proven.
6. Extract shared fixture builders only when they replace repeated setup in multiple surviving tests.

### Files

Primary:

- `Tests/OpenMarkedCoreTests/AppInfoTests.swift`
- `Tests/OpenMarkedAppTests/*.swift`

### Deletion Targets

- Parallel XCTest and Swift Testing definitions for the same behavior.
- Duplicate fixture setup.
- Duplicate assertion helpers.

### Performance Target

Test runtime may improve, but the main target is lower refactor risk and faster future iteration.

### LOC Target

Remove well over 1,000 lines of duplicate test code while preserving behavior coverage.

### Tests

The validation is the test run itself:

```sh
swift test
swift run OpenMarkedVerifier
```

## File Watcher Follow-Up

The 0.5.1 watcher strategy already improved image-heavy documents. During 0.5.2, only touch watcher code if the shared HTML index makes asset data cheaper to pass through.

Potential low-risk change:

- Feed asset watcher reconciliation from `RenderedHTMLIndex.images`.

Potential later change:

- Share watcher queues or add a dedicated directory asset watcher.

Defer the later change unless measurements show watcher overhead remains a top issue. It is more invasive than the parsing and cache work.

## Risk Register

### Risk: Shared Scanner Changes Extraction Semantics

Mitigation:

- Add fixtures before migration.
- Keep compatibility wrappers until all call sites pass tests.
- Compare old and new extraction output in temporary tests during implementation.

### Risk: Sanitizer Blocks Legitimate Raw HTML

Mitigation:

- Capture current allowed URL behavior in tests.
- Only block clearly unsafe schemes and event/script behavior.
- Keep data image behavior only if existing fixtures require it.

### Risk: Caches Return Stale Files

Mitigation:

- Key user-theme and cross-document heading caches by file signature.
- Invalidate user-theme cache on managed-store mutations.
- Keep cross-document heading cache per render.

### Risk: Resource Extraction Adds Package Complexity

Mitigation:

- Reuse existing core resource loading if that is smaller than adding app resources.
- Choose the option with the least package and loader code.

### Risk: State Save Debounce Loses Latest State

Mitigation:

- Implement in-memory cache first.
- Add debounce only if still needed.
- Flush synchronously on close if debounce lands.

## Expected Net Result

Runtime:

- Fewer full-string scans during render.
- Fewer regex compilations and repeated attribute parsers.
- Fewer disk reads from theme and rich content paths.
- Less SwiftUI work during view invalidation.
- Faster cross-document link validation.
- Faster repeated preview search.

Codebase:

- One HTML tag scanner instead of several partial regex extractors.
- One Markdown heading scanner instead of multiple heading parsers.
- One diagnostic metadata source instead of duplicated app extensions.
- Cached theme/resource stores instead of repeated construction and reads.
- Smaller `PreviewWebView.swift`.
- Smaller test suite with equivalent behavior coverage.

Release readiness:

- Ship `0.5.2` as a performance and safety release.
- Document that behavior is intended to match `0.5.1`.
- Call out stronger raw HTML safety as a compatibility note only if any previously unsafe construct is now blocked.
